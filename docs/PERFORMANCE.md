# MEETI パフォーマンス改善（2026-10-22）

## 対象と作業場所

GitHub最新状態をfetchし、`origin/main` の `e1d55ab` を土台に `perf/ios-responsiveness-20261022` を作成しました。mainには複数端末のSupabase共有が追加されており、古いfeature/yunaだけを改善すると共有機能を落とすためです。元の作業フォルダと未コミットのXcode状態ファイルは触らず、別チェックアウトで作業しています。main・feature/yunaへの直接変更やマージは行いません。

## 最優先：撮影後、プロフィール画面のスクロールが固まる報告

実機の機種・OS・継続時間は未確認です。次のコード上の問題は確認しましたが、フリーズの原因を実機で確定したわけではありません。

1. `CameraPicker` はカメラの完了コールバック内で元の大きさの写真をJPEGへ変換していました。UIを操作するメインスレッドで長い処理が走ると、スクロールやタップの処理も待たされます。
2. `ProfileInputView.body` 内で `UIImage(data:)` を呼び、写真を読み直していました。bodyはSwiftUIが画面を評価する場所で、写真・文字入力・趣味選択などの状態変化で再評価されます。実際の展開は描画時にも発生するため、読み込みと大画像の描画を繰り返す経路です。画面のframeを150ptにするだけでは元写真の画素数は減りません。
3. 元の写真Dataは診断・保存まで保持されます。Dataの受け渡しは共有される場合があり、「引数の数だけ写真が丸ごと複製される」とは断定できません。ただし元解像度の画像展開とJPEG変換の一時メモリは別に必要です。

### 対応

- カメラのJPEG変換をバックグラウンドへ移動。圧縮率0.8、元写真のサイズ、写真の保存形式を維持しました。キャンセル後に古い変換結果が反映されないよう制御しています。
- プロフィール写真は写真Dataが変わったときだけ、バックグラウンドで最大1024pxへ縮小。完成画像をState（画面が保持する一時状態）へ格納します。bodyではJPEGの読み込み・縮小・ハッシュ計算を行いません。
- 元のphotoDataは変更しません。表示画像だけを縮小するため、保存・アップロードの画質設定を変えません。現在の最大210pt程度の写真表示では3倍解像度の630pxより大きい1024pxを確保しています。将来写真を大きく拡大するUIを追加するときは見直しが必要です。
- 撮り直し・削除で前の非同期処理が遅れて完了しても、新しい画面を上書きしないようキャンセルを確認します。

N人全員に写真があり、同率BEST MATCHがW人なら、初回の写真取得対象はN枚からW枚です。これはコード上のリクエスト数の説明で、通信時間の実測ではありません。同率全員が選ばれた場合は削減できません。プロフィール自体は従来どおり全員分を取得します。

条件変更中は古い処理をキャンセルし、古い結果で上書きしないようリクエストを識別します。同じ画面内の条件変更ではプロフィールを再利用し、画面を離れて戻った場合には他端末の新規参加者を再取得します。認証・匿名ログイン・通信エラー時の表示・写真取得失敗時のMBTI画像フォールバックは維持します。

## 維持したもの・残るリスク

Participantのスキーマ、SwiftDataの既存データ、MBTI診断・相性計算・同率全員表示・本人除外、画面の順序、画像の切り抜きとレイアウト、CardURLBuilder、Web名刺、Supabaseの設定・認証情報は変更していません。大きな元写真の保存データ自体は残すため、保存領域の増加は解決していません。

初回の写真表示まで短い非同期準備期間があります。プロフィールでは従来の人物プレースホルダーが出る場合があります。他の名刺のキャッシュ初回ミスでは縮小処理がメインアクターに残り、写真Dataのハッシュ計算も必要です。これは再測定後の追加改善候補です。上限付きキャッシュは保持の目安であり、プロセス全体のメモリ上限ではありません。

全参加者のプロフィール取得・モデル作成・相性計算は件数に比例します。サーバーの返却件数上限や大量の同率結果は従来からの確認事項です。取得件数や順位を勝手に変える最適化はしていません。通信が遅い場合やStorageにアクセスできない場合は写真取得時間が残ります。

## iPhoneとInstrumentsでの確認手順

1. チームで同じiPhoneを使い、機種・iOS・空き容量・バッテリー・発熱・低電力モード・Wi-Fiを記録。元main(e1d55ab)と改善ブランチを同条件のReleaseで比較する。実データを消さず、検証用アカウント・データを使う。
2. XcodeのProduct > ProfileからTime Profilerを起動。Main Thread（タップやスクロールを扱う処理列）とHangs（応答しない区間）を記録できる場合は追加する。
3. 写真なしでプロフィールを10秒スクロールし、写真撮影→カメラを閉じる→すぐ上下スクロール→名前を入力→趣味を連続選択する。同じ操作を5回。縦横写真・撮り直し・削除・撮影キャンセルも確認する。
4. 撮影完了からプロフィール表示までと、スクロールが反応しない区間の長さを記録。JPEG変換、CGImageSource、画像描画がMain Threadで長時間走っていないか比較する。改善前に再現しなかった場合も、その事実を記録する。
5. Allocations（メモリ確保の履歴）とVM Trackerで、撮影直後・プロフィール・名刺・終了後の使用量と最大値を比較。大きなUIImage/画像バッファが操作ごとに増え続けないかを見る。Memory Graphも使用する。
6. 同じ参加者数、写真数、同率人数、フィルタ条件でマッチングを測る。NetworkでStorageの写真リクエスト数・転送量を確認し、選ばれた相手以外をダウンロードしていないことを確認する。性別・年代を素早く切り替えて古い結果が戻らないことも確認。
7. 診断12問・直接選択・参加者保存・全員からのBEST MATCH・同率表示・相手の写真・本人除外・QR画面への本人受け渡しを確認。写真の向きと見た目を比較する。
8. QRを別スマホで読み取り、Web名刺の名前・MBTI・写真・公開期限を確認。運営ログインあり／匿名、写真なし、通信切断・再試行、トークン再利用も確認。
9. 体験終了→Startへ戻る→次の参加者で入力欄が初期化され、保存済み参加者は残ることを確認。10人分繰り返し、メモリが増え続けないか測る。
10. 各5回の中央値・最大停止時間・最大メモリ・転送量を表にし、Instrumentsのtraceを個人写真や認証情報が公開されない場所に保存する。

## 追補：PhotoThumbnailのXcodeターゲット登録漏れを修正

`PhotoThumbnail.swift`はGitとSwift Packageのテストには含まれていましたが、従来形式のXcodeプロジェクトには自動追加されず、MEETIアプリのCompile Sourcesへの登録が抜けていました。このためProfileInputView等から型を参照できませんでした。

project.pbxprojのPBXFileReference、MEETIグループ、PBXBuildFile、PBXSourcesBuildPhaseへ登録しました。動作や画像処理ロジックの変更はありません。テストコードとベンチマークの@mainはアプリには追加していません。

再発確認：`python3 Tools/check_app_sources.py`。Xcodeプロジェクトをplutilで解析し、全30個のアプリSwiftファイルがSourcesに一度ずつ含まれることを確認します。`--write-file-list /tmp/meeti-app.SwiftFileList`で実際のターゲットの一覧を出力できます。

検証結果：プロジェクト構文検証・全30ファイルの登録検査・14テスト・diffチェック成功。ターゲットから抽出した30ファイルを既存のSupabase依存モジュールとiOS18向けSwiftコンパイラでオブジェクトコードまでコンパイル成功。既存のSupabase非推奨API警告2箇所は残っています。xcodebuildは再実行したもののSwiftPMのキャッシュ書き込み権限で依存解決が停止し、完全なXcodeビルド成功は確認できていません。
