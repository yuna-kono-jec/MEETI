# 2026-10-23 撮影後のプロフィール入力の重さへの対応

## 確認したコードと症状

- 共有リポジトリは `yuna-kono-jec/MEETI`。取得時の最新mainはTaeさんの `f88a132`。
- 作業ブランチは `perf/ios-responsiveness-20261022`。`fe1402b`でTaeさんのmainを取り込み、共有mainへの反映前に追加修正を検証した。
- 利用者から確認した症状は「プロフィール入力で、写真を撮った後に重くなる」。その後の画面はまだ実機で確認できていない。
- 下記はコード・仮画像・Macでの確認結果。実機の停止時間を測った結果ではなく、写真処理を有力な原因として改善したもの。

## 原因候補と修正

| 場所 | 確認した処理 | 対応 |
| --- | --- | --- |
| 撮影完了 | mainでは撮影したフルサイズ写真を画面操作と同じ処理場所でJPEG化 | 既存の作業ブランチにあるバックグラウンド変換を維持 |
| プロフィール | mainでは元写真をUIImageにして表示。表示枠を小さくしても元画像の画素数は減らない | 写真が変わったときだけ最大1024pxの表示用画像を別処理で作り、入力中は再利用 |
| 名刺・相手の写真 | 作業ブランチでは画面更新中に写真のハッシュ計算と初回の縮小が走る | それらもバックグラウンドに移動。画面には作成済み画像だけ渡す |
| マッチング | 作業ブランチでは同率相手全員の写真が揃うまで結果を待つ | Taeさんの最新mainに合わせ、プロフィールだけで結果を出して写真は表示時に取得 |
| 同率結果 | 全カードを最初に作る通常のVStack | LazyVStackで見える範囲から表示。人数や同率条件は変更なし |
| 参加者一覧 | 日付変換用の道具を参加者ごとに作り直す | 2種類の形式を再利用。25人ごとにキャンセルを確認し、他の処理に実行機会を渡す |

撮影し直したり画面を離れたりした場合は、古い画像処理の結果で新しい表示を上書きしない。画像を読めなかった場合は既存のMBTI画像で表示を続ける。ローカルの画像が壊れていてリモートの保存先がある場合は、リモート画像を試す。

## 変更していないもの

- Supabaseの接続先・キー・認証方法・権限・保存する項目。本番への参加者登録や設定変更は行っていない。
- Participantのモデル構造とSwiftDataの既存データ。元写真の保存サイズ・JPEG品質設定も維持。
- MBTI診断、相性配点、自分の除外、性別・年代条件、同率1位、候補0人の処理。
- 画面のデザイン、写真の切り抜き方、QRの内容と公開期限。
- ユーザーのDeployment Target 17.6、名刺の「マッチングへ進む」とコメント、Xcode画面状態の変更を保護。名刺ファイルには画像表示の修正だけを追加。

## 検証

- 16件の単体テストが成功（既存ロジック9件、画像7件）。画像サイズ・向き・キャッシュ・無効な写真・キャンセル・画像処理中に別の画面処理が進めることを確認。
- Xcode 26.3でシミュレータ向けアプリ全体のDebugビルド成功。これは実機iOS 18での動作確認とは別。
- iPhone 16e / iOS 26.3シミュレータで、起動→プロフィールの文字入力→好きなこと3件選択→診断画面への移動→戻る操作を確認。写真なしの基本操作で停止は再現しなかった。テスト入力は登録せず終了した。
- Xcodeプロジェクト構文、全30個のSwiftファイルのターゲット登録、差分形式を検査。
- 実機のカメラ撮影から入力操作までの確認は未実施。登録・写真公開など本番データを書き込む検証も未実施。

### 仮画像・仮参加者の測定（Macのみ）

4032×3024の仮JPEG、最適化したSwift、15回の中央値。フル画像の展開は17.560ms、初回縮小は25.214ms、縮小画像の再利用は0.214ms。初回縮小そのものが速いわけではなく、入力を処理する場所で実行しないことが重要。

展開した画像のバッファは48,771,072 bytesから3,145,728 bytesに減少。これはアプリ全体のメモリ使用量ではない。

1000人分の日付文字列の変換では、変換用オブジェクトを毎回作る場合223.0ms、再利用48ms程度。同じMac上の仮データによる単体比較であり、通信やiPhoneの速度は含まない。

## 実機で次に確認すること

1. この作業フォルダからビルドして、同じiPhoneで写真なしの入力・スクロールを確認する。
2. 写真を撮り、名前入力・好きなこと選択・上下スクロールを続ける。
3. 撮り直し、写真削除、撮影キャンセルでも古い写真が戻らないか確認する。
4. 名刺、マッチング結果、QRへ進んでも写真の向きや内容が変わらないか確認する。
5. まだ重い場合は機種・iOS・どの操作が止まるかを記録し、InstrumentsのTime Profiler/Hangsで実機の処理を測る。

取得件数の上限・通信障害・大量参加者へのページングなどは別の確認事項。今回の修正だけで、本番の複数実機共有や全画面の速度が保証されたとは扱わない。
